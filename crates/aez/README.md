# rings-aez

AEZ v5 (Hoang, Krovetz and Rogaway, [AEZ v5: Authenticated Encryption by Enciphering](https://www.cs.ucdavis.edu/~rogaway/aez/aez.pdf))
on top of the RustCrypto `aes` round function, for native and `wasm32-unknown-unknown` targets.

AEZ enciphers `M ‖ 0^τ` with a tweakable, arbitrary-input-length blockcipher. The same key
therefore serves two roles, which the Rings onion carry (#834) uses one per hop:

| role | operation | property |
|---|---|---|
| relay | [`Aez::encipher`] / [`Aez::decipher`] (`τ = 0`) | length-preserving tweakable strong PRP on every length |
| consumer | [`Aez::encrypt`] / [`Aez::decrypt`] (`τ = 16`) | robust AE: any change to any ciphertext bit fails authentication |

Owned buffers carry the length precondition and the plaintext/ciphertext distinction as types:
[`Aez::seal`] maps a [`Plaintext<τ>`](Plaintext) (wiped on drop, opaque) to a
[`Ciphertext<τ>`](Ciphertext) (`|C| ≥ τ`) without failure, and [`Aez::open`] maps it back or
rejects it. Both paths share one private encryption and one decryption core with the slice API.

## Model

```text
Block      GF(2^128), big-endian bit order; ⊕, X ↦ 2·X, k·X              block.rs
E^{j,i}    AES4(X ⊕ j·J ⊕ 2^⌈i/8⌉·I ⊕ (i mod 8)·L),  E^{−1,i} = AES10(X ⊕ i·L)   tbc.rs
Δ          AEZ-hash_K([8τ]_128, N, A_1, …)                                hash.rs
Encipher   AEZ-tiny (1–31 bytes) | AEZ-core (≥ 32 bytes)                  aez_tiny.rs, aez_core.rs
Encrypt    M = ε ↦ AEZ-prf(Δ, τ);  M ≠ ε ↦ Encipher_Δ(M ‖ 0^τ)             lib.rs
```

Laws witnessed by the tests: `decipher ∘ encipher = id` and `decrypt ∘ encrypt = id` for
every length and tweak shape, equality with the reference implementation on the committed
known-answer vectors, and rejection of every single-bit change at `τ ≥ 4`.

## Keys

A key is exactly 48 bytes, `K = I ‖ J ‖ L`, for which AEZ's `Extract` is the identity. A key
with a zero subkey is rejected ([`KeyError::ZeroSubkey`]; Mennink, CT-RSA 2017). AEZ's
security is birthday-bound per key (≈ 2^64 blocks; the key-recovery attacks of Fuhr–Leurent–Suder
and Chaigneau–Gilbert need that volume under one key), so a key should process few messages.

## Side channels

- AES rounds come only from `aes::hazmat::cipher_round`: AES-NI on x86, fixsliced
  table-free software AES elsewhere (including `wasm32` and, without `--cfg aes_armv8`,
  aarch64).
- Field doubling and scalar multiplication are branch-free in the block value.
- The authenticator check is a constant-time comparison; a failed [`Aez::decrypt`] zeroizes
  the buffer, so unverified plaintext is never released.
- Subkeys are zeroized on drop. Intermediate blocks on the stack are not.
- No `unsafe`.

## Known-answer vectors

`vectors/reference.txt` is generated by `vectors/generate.c` from the official reference
code (`aez5_software.zip`, `crypto_aead/aezv5/ref/`); the header of `generate.c` records the
archive digest, the build command and the line format.
